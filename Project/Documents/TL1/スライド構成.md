## 6枚目：Blender連携③　座標を一致させるための実装

> 加点条件「位置や回転が Blender とゲームで一致している」の直接の証拠。技術難易度もここで示す。

### 文字コンテ

```
見出し：座標系の違いを吸収し、往復しても値が変わらないようにした

・回転行列の合成順が2種類あり、実際に配置へ使われる順（Rx·Ry·Rz）に合わせて変換した
・glTF はカーブを表現できないため、スプラインの制御点を自前でワールド座標へ焼いて受け渡す
　　→ Blender ⇄ エンジンの往復で制御点の誤差 0.0 を実測
・アセットは必ず原点で書き出し、配置はシーンJSON側に持たせて二重変換を防いだ
```

### 画像

- **座標変換の図解（自作）**：Blender(右手系Z-up) → エンジン(左手系Y-up) の変換を軸の絵で示す
- **スプラインの往復スクショ**：Blenderのベジェカーブと、ゲーム内のCatmull-Romスプラインを並べ、制御点に番号を振って対応を示す
- 誤差 0.0 は**テスト出力のコンソールを小さく貼る**と説得力が出る

## 9枚目：アセットコンバータ ＆ パッケージャ

> 既存スライドの作り直し。**DirectStorage / GDeflate が抜けているのが最大の損失。**

### 文字コンテ

```
見出し：素材を置いてビルドするだけで、配布用パッケージまで自動で出来上がる

・Assets フォルダに入れてビルド → PNG→DDS(BC7)、OBJ/glTF→.mesh/.mat/.skel/.anim へ自動変換
・変換済みアセットを 1つの .pack に集約
・GDeflate で圧縮したまま DirectStorage 1.4 で GPU へ送り、CPU を経由せず展開する

工夫：法線マップの有無を見て PBR シェーダーへ自動で切り替えるので、変換設定を手で書かなくてよい
効果：ロード時間 ●●秒 → ●●秒〔要実測〕／VRAM ●●MB 削減〔要実測〕
```

### 画像

- **パイプライン図（自作・このスライドの主役）**：
  `Assets/*.png,*.obj,*.gltf` →［cook_assets］→ `Resources/*.dds,*.mesh` →［pack_assets + GDeflate］→ `Assets.pack` →［DirectStorage］→ GPU
- 図の下に**CPU経由の従来経路と、GPU直行の自作経路を上下2本並べて対比**すると難易度が伝わる
- ロード時間の**棒グラフ**（before/after）。数値が測れない場合はグラフごと省く

## 10枚目：P.E.P.P.E.R.（自作プロファイラ）

> 既存スライドの作り直し。「わかる」で終わらせず「直せた」まで書く。

### 文字コンテ

```
見出し：重い区間をその場で特定し、直した結果まで確認できる

・ゲーム内オーバーレイで CPU/GPU の区間時間・ドローコール数・VRAM 使用量を毎秒表示
・ログを解析して「最も遅い区間」を file:line 付きで一覧できる
・60fps のフレーム予算に対する占有率で表示するため、直すべきかどうかを即断できる

工夫：計測はログを書くだけでゲームの乱数や経過時間に触れないため、
　　　後述の無人自動検証（決定論リプレイ）と同時に動かせる
実例：●●の区間が ●●ms → ●●ms に短縮〔要実測〕
```

### 画像

- **オーバーレイのスクリーンショットを大きく**（現行スライドは小さすぎる）。読ませたい行を赤枠で囲い、引き出し線で「ここが最も遅い区間」と注記
- **解析ツールの出力（TopN一覧）のコンソール画面**を併置
- 可能なら**改善前後の2枚**を並べる。これがあると実用度の評価が一段上がる

## 11枚目：S.U.N.D.A.Y.（無人自動検証）

### 文字コンテ

```
見出し：寝ている間にゲームを遊び倒し、バグを見つけて報告させられる

・仮想ゲームパッドでゲームを自動操作し、ハング・スタック・座標の破綻・クラッシュを検知
・検知したら GitHub の Issue に自動で起票する

工夫：乱数シードと毎フレームの生入力を記録する決定論リプレイを持ち、
　　　「本当に再現するか」を自動で確かめてから起票するので、再現しない報告が積み上がらない
```

### 画像

- **処理フロー図（自作・主役）**：
  `自動プレイ` →`ログ監視` →`異常検知` →`同じシードで再生` →`再現した？` →`Yes: Issue起票 / No: 破棄`
  分岐を菱形で描くと「再現性を確かめている」ことが一目で伝わる
- **実際に起票された GitHub Issue のスクリーンショット**。これが最も強い証拠になるので必ず入れる
- 検知ログ（anomalies）の抜粋を小さく添える

## 撮影・作成時の共通ルール

- **スクリーンショットは等倍で撮って縮小する**。拡大すると文字が潰れて読めない
- **読ませたい箇所は必ず赤枠＋引き出し線**。スライドは1秒で焦点が定まらないと読み飛ばされる
- **ゲーム画面とツール画面は必ずセットで映す**（課題の「ゲーム側で出力結果が反映されるのが確認できること」に対応）
- 自作の図は Google スライドの図形機能で足りる。色は3色以内に抑える
- 〔要実測〕の数値が埋まらない行は**削除する**。推定値を書かない

## 動画との対応

解説順はスライドと揃える指定。撮影順序は以下を推奨（**双方向同期を冒頭に置く**のが最も掴みが強い）。

1. Blender ⇄ エンジン同期（画面2分割で同時に動くところ）
2. 敵ウェーブ配置エディタ（スクラブ→ドロップ→再生）
3. エフェクトエディタ（数値変更→即反映）
4. アセットコンバータ（素材追加→ビルド→ゲームに出る）
5. プロファイラ（オーバーレイ表示）
6. S.U.N.D.A.Y.（自動プレイ→Issue起票）
7. モーションキャプチャ（実写→ゲーム内モーション）
8. J.A.R.V.I.S.（スマホ操作→PC画面が動く）
