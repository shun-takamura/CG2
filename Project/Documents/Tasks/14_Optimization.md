# 14. 最適化

> **目的: 最適化の余地を 1 か所に集める。** 各設計書で見つかった「重い所」と「軽くする候補」をここに書き、実施したら前後の実測を残す。
> 評価は動画＋ソース審査なので、**「自作プロファイラで測る → 原因を特定 → 直す → 測り直す」の記録そのものが語れる材料**になる。

最終更新: 2026-10-10

---

## 1. 書き方の決まり

- **1 件 = 1 節**。見出しは「対象（どの区間・どの場面）」。
- 必ず書く項目：

  | 項目 | 内容 |
  |---|---|
  | 状態 | 未着手 / 実施中 / 実施済み / 却下 |
  | 実測 | PEPPER の区間名と ms（ビルド構成・解像度・場面・日付）。未計測なら「未計測」と書く |
  | 原因 | 何が重いのか（推定なら推定と書く） |
  | 候補 | 軽くする案を、効果が大きく手間が小さい順に。見た目が変わるかも書く |
  | 元 | 見つけた設計書と節（例：9番 実測） |

- **実施したら**：前後の実測を同じ条件で取り、§5「実施済み」へ移す。却下した案も理由を残す（同じ案を二度検討しないため）。
- **計測は Development で取る。** Debug は D3D12 のデバッグ層が有効で、シェーダも最適化なし（`-Od`）の実行時コンパイルなので GPU 時間が過大に出る。
- 元の設計書には元の記述を残し、候補の追加・更新はここで行う。

## 2. 計測の道具

| 道具 | 使い方 | 出るもの |
|---|---|---|

## 4. 候補（優先順）

### 4.1 雲のレイマーチ：降下中（入口〜出口の約 10 秒）

- **状態**：未着手
- **実測**：`CloudRaymarcher::March` 0 秒 0.31ms → 53 秒 **5.71ms**（フレーム 17.49ms で 60fps 割れ）／60 秒 5.21ms。`run_cloud_bench.py --preset stage-raymarch --seconds 20`、Development・RT 1/2 解像度、2026-10-10
- **原因**：
  - 穴のまわりの濃さ（`HoleOver`）：壁 2 面＋天井（その場所の上面の高さも引く）＋床で、ノイズの読み込みが通常の約 6 倍
  - B'（雲の中のもや）：1 歩ごとに濃さ 3 回（本体＋太陽側 2 タップ）× 3D 勾配ノイズ 2 オクターブ、48 歩
  - 縦穴のまわりの法線：濃さの中心差分で 6 回
- **候補**：
  1. `HoleOver` の天井・床を、その高さの近くにいる時だけ評価する（ほとんどの点は壁だけで済む）。見た目は不変
  2. B' の太陽側 2→1 タップ（B' 約 3 割減）。陰影が少し平らになる
  3. `volumeSteps` 48→32（B' 約 3 割減）。もやが少し粗くなる
  4. 3D ノイズを 1 オクターブ、または 3D テクスチャ（計算 → 読み込み 1 回）
  5. 降下中だけ RT を 1/2 → 3/8 解像度（全体が比例して減る）
  6. 縦穴のまわりの法線を中心差分（6 回）から前進差分（3 回＋手元の値の流用）に
- **目標**：60fps を保つには最低 1ms。①と②で届く見込み
- **元**：9番「実測」

### 4.1b 雲のレイマーチ：雲海の上（ハイトマップ誘導のボリューム雲）

- **状態**：却下（2026-10-22、ユーザー判断で旧方式に戻した。`hvEnabled` 既定 false で比較用に残す）
- **実測**：`CloudRaymarcher::March` 旧方式（高さ場＋法線）**0.313ms** → 新方式 **2.690ms**（0 秒・雲海の上、`run_cloud_bench.py --preset stage-raymarch --holds 0 --seconds 20`、Development・RT 1/2、2026-10-22）。60fps は保てている（フレーム 16.71ms）
- **原因**：綿の層 24 歩 ×（濃さ 1 回＋太陽側 4 回）。濃さ 1 回ごとに上面の高さ 2 回（ずらしの判定と本番）＋3D 勾配ノイズ 4 回（ずらし 2・崩し 2）。勾配ノイズは 1 回で 8 回ハッシュ
- **候補**：① 3D ノイズを 3D テクスチャに（計算 → 読み込み 1 回）② 太陽側 4→2 点 ③ ずらしの判定に使う上面の高さを使い回す ④ 歩き方の揺らし＋TAA で歩数 24→8〜12 ⑤ 遠いほど歩数を減らす
- **元**：9 番 17〜19 回目

### 4.1c 雲のレイマーチ：雲海の上（ボリューム＋時間方向の積み重ね、採用候補）

- **状態**：実装済み（2026-10-23、`volumeSea` 既定オン）。ユーザー確認待ち
- **実測**：`CloudRaymarcher::March` **0.75ms**（0 秒）／**0.94ms**（25 秒）／0.78ms（45 秒）、`::Temporal` 0.02ms、`::Composite` 0.03ms（`run_cloud_bench.py --preset stage-raymarch --holds 0 25 45 --seconds 12`、Development・RT 1/2）。歩数 64 で 1.53ms、32 で 0.65ms（25 秒）＝ほぼ歩数に比例
- **やったこと**：4.1b の候補 ①（3D テクスチャ）④（揺らし＋積み重ねで歩数を減らす）。上面の高さは光側の近い 2 点で使い回し、マスクは画素ごとに 1 回（効果は小さかった：1.28→1.24ms）
- **さらに削るなら**：① チェッカーボード（毎フレーム半分の画素だけ歩き、残りは積み重ねから）でほぼ半分 ② 遠いほど歩数を減らす ③ 太陽側の遠い 2 点（大きな塊の影）を 1 点に
- **元**：9 番 27 回目

### 4.2 地形の描画（ピクセルシェーダの塗り）

- **状態**：未着手（2026-10-25 の Development で低空 54〜55fps と 60fps を割った。L9 のストリーミングの後で着手を検討）
- **実測**：`Scene::DrawDynamicObjects`（地形込み）高高度 0.4〜0.7ms → 降下〜低空で地形が画面を埋めると **5〜8.7ms**。2026-10-08、Debug ログ（`Project/Logs/2026-10-08_223738` ほか）。影のパスは GPU 区間が無く未計測。**2026-10-25（Debug、`Logs/2026-10-25_005914`）低空で 41〜44fps**：測れている GPU 約 10.5ms（地形 5.5〜6・水面 1.8・反射 1.5・空 1.6）に対しフレーム約 23ms → 未計測の所（影のパスが最有力）。同日 `Game::ShadowPass` に GPU 区間を足した（候補 4 の前半）。**同日 Development（`Logs/2026-10-25_011814`）：低空 71〜75 秒で 54〜55fps。地形 6.2〜6.5ms・影 2.4ms・水面 1.8・反射 1.5・空 1.6〜1.8（GPU）、合計約 14ms＋ポストエフェクトで予算を少し超える。主因は影ではなく地形の塗り** → 次にやるなら候補 1（見た目不変）。Debug の数字はシェーダの `-Od` で大きく出るので判断は Development で。蛇行・滝の区間は未計測
- **原因**：頂点数は一定で、画面を埋めた時だけ増える → 地形 PS の塗りが主因とみる（推定）
- **候補**：
  1. 重みが 0 の層はテクスチャを引かない分岐（`Terrain.PS.hlsl:185-187`。岩の三平面 12 回・土 4 回を飛ばせる）。見た目は不変
  2. 岩の三平面投影で寄与の小さい面を飛ばす
  3. 異方性 16→8
  4. 影のパスに PEPPER の GPU 区間を足して頂点側も測る → 必要なら遠くの地形の LOD／チャンク分割＋視錐台カリング
  5. 三平面投影・2 スケールのサンプル数を減らす
  6. 影のカスケードの比率（`SetCascadeLambda`）の調整
- **元**：12番 §7・§8 後回し、11番 §3.4（L2→L8）

### 4.5 スキニング・アニメーション（分身カウンター）

- **状態**：未着手（**機能のブロッカー**：分身のアニメ再生が性能理由で入れられていない）
- **実測**：スキン付き 4 体で fps が 40 台後半（計測済み、数値の記録は 8番）。PEPPER での区間計測は未実施
- **原因**（コード読解による推定。GPU のスキニングではなく CPU のアニメ適用）：
  - `ApplyAnimation` が毎フレーム・毎ジョイントで `std::map<std::string, NodeAnimation>` を文字列検索（`Skeleton.cpp:64`、ブレンド中は `:86`・`:95` で 2 回）
  - キーフレーム探索が毎回先頭からの線形走査（`Animation.cpp:79-86`）
- **候補**：
  1. ロード時にジョイント → チャンネルを事前解決して配列に持つ（毎フレームの文字列検索が消える）。効果大・手間小
  2. キーフレーム探索のカーソルキャッシュ（前回のインデックスから再開。逆再生・シークは 0 へ戻す）。効果大・手間小
  3. `DispatchSkinning` のバリア→Dispatch→バリアを全インスタンスでまとめる（`AnimatedObject3DInstance::DispatchSkinning`、`AnimatedObject3DInstance.cpp:201` 〜）。①②で足りなければ
- **進め方**：まず PEPPER で現状を測る（分身をスキン付きに戻した状態で）→ ① → 再計測 → ② → 再計測
- **元**：8番 §4

### 4.6 谷：岩柱・梁のそばを通る所

- **状態**：実施中（2026-10-29 案 1 をコードまで・ビルド・実機未確認。`RailStagePart` の退避トリガーで、enemy_type "Obstacle" と地形に置いた `Static`（砲台）は `retreat_sec` に消す。`gen_canyon_wave.py` が通過の 3 秒後を `retreat_sec` に書く。崩れた根元は残る）
- **案 1 の実測**（Development `Logs/2026-10-29_172911`、前の回 `163056` と同じ通し）：`Scene::DrawDynamicObjects` の山は 134〜139 秒 12〜13 → 9.7〜11ms、146〜150 秒 11.7〜14.4 → 8.8〜12.5ms。fps は 49〜55 → 50〜59（148〜151 秒はまだ 50〜56）。ただし谷に入る前（104〜121 秒）も 1ms ほど低く出ているので、回ごとのぶれが 1ms ほどある。残りは近くの岩と奥の壁の塗り（案 2・3）
- **実測**：Development `Logs/2026-10-29_163056`（雲の上から通し）。`Scene::DrawDynamicObjects` は障害物の無い 122〜124 秒で 4.7〜5.1ms、岩柱・梁のそばを通る 134〜139 秒・146〜149 秒で 12〜14.4ms（49〜55fps）。126 秒に低空の地形を消した後は `Game::ShadowPass` が 2.0 → 1.1ms に下がった
- **原因**（推定）：カメラが岩の 1〜2m そばを通るので、岩（PBR）が画面の大部分を塗る＋その奥の峡谷の壁（地形 PS、4.2）の重ね塗り。通り過ぎた障害物は壊されるまで残る（`ObstacleCommand` は退場しない）ので、後ろの岩も描いている可能性。岩ごとの区間はまだ測っていない
- **候補**：
  1. 通り過ぎた障害物を消す（カメラの後ろ数十 m で `retreat` 相当。見た目は変わらない）。効果は描く数次第・手間小
  2. 4.2 の地形 PS の軽量化（重みが 0 の層を飛ばす等。見た目は不変）
  3. 岩の PBR を軽い材質にする／近い岩だけ LOD（見た目が少し変わる）
- **元**：11番 §6 S5、4番 §11

### 4.7 ステージ全体：1 フレームだけ 15〜50ms 止まる（CPU）

- **状態**：未着手（原因の特定まで。2026-10-29 谷の担当が PEPPER の区間を足して調べた）
- **実測**：Development `Logs/2026-10-29_184514`（雲の上からボス戦まで通し）。止まった秒の `SceneManager::Update` の下に出た区間：
  | 止まり | 区間 | 大きさ | いつ |
  |---|---|---|---|
  | ① 弾・敵を出す | `InstantiatePrefab::AddPrimitive`（エンジン `Scene::AddDynamicPrimitive` → `PrimitiveInstance::Initialize`） | 1 個 0.5〜2ms。ボス戦で敵弾を 1 秒に 20〜40 個出すと **37〜49ms** | ステージ全体（26・62・84・108 秒…、ボス戦 186〜196 秒） |
  | ② 名前を一意にする | `InstantiatePrefab::UniqueName`（＋エンジンの `AddDynamicPrimitive` の中にも同じループ） | 物の数の 2 乗。板 103 個で 10ms | 弾が多い時 |
  | ③ 初めて出るモデル | `InstantiatePrefab::AddObject3D` | 46ms（1 回） | 11 秒（最初の敵） |
  | ④ エフェクトの更新 | `EffectManager::UpdateInstances` | 13〜26ms。動いているエフェクトは 4 個だけ | **約 30 秒おき**（1・30・61・90・151・180 秒） |
  | ⑤ エフェクトの片付け | `EffectManager::PendingDelete` | 8ms | 199 秒 |
  | ⑥ 区間の空の差し替え | `StageEnvironment::Update`（谷の区間の夜の cubemap `rogland_clear_night_4k.dds` を同期で読む） | 39ms | 谷の区間に入る所（`Logs/2026-10-29_182803` の 125 秒） |
- **原因**：
  - ① 弾 1 発ごとに `PrimitiveGenerator::CreateSphere` で形を作り直し、`mesh_.Initialize` で頂点・インデックスのバッファを新しく作っている（同じ形を毎回作る）
  - ② 同じ名前が無くなるまで全部の物と比べ直す（`name (1)`, `name (2)` … と毎回 1 から数える）
  - ③ Wave で出るプレハブのモデルを開始時に読んでいない（谷の分だけは `StageStreaming` の `prefabs` で読むようにした＝11番 §6 S5）
  - ④ 4 個のうちのどれか（ループするエフェクト？）が約 30 秒ごとに重い処理をしている（未特定。`EffectInstance::Update` の中を分けて測る）
- **候補**：
  1. ② 実行時に出す物は連番のカウンタで名前を付ける（または名前を付けない）。手間小・見た目は不変
  2. ① 形ごとにメッシュを共有する（型＋パラメータでキャッシュ）、または弾をプールして使い回す。効果大・エンジンの変更（ArcanaEngine 同期）
  3. ③ ステージの開始時（HUB の降下の先読み）に Wave の全プレハブのモデルを読む
  4. ④ `EffectInstance::Update` を分けて測り、どのエフェクトかを特定する（エンジン）
  5. ⑥ 谷の区間の空をほかの区間と同じ青空にする（読み込みが無くなる。背景は青空＋雲の方針。L5 の値）
- **元**：11番 §6 S5（谷の担当の計測）

### 5.2 雲：板の雲とレイマーチの比較（判断の記録）

- 板の雲（smoke_00 の Plane）は**重なり画面 1 枚分 ≈ 0.04ms でほぼ線形**（100 枚 0.08ms → 800 枚 0.77ms）。高高度の雲海を埋めるなら 200〜400 枚で 0.2〜0.4ms、雲に近づくと 1〜2ms 以上に跳ねる見込み。
- レイマーチ（ゼノブレ式の面）は雲海の上で 0.31ms。**同じ桁で、近づいても量を増やしても一定**、雲を抜けられる → レイマーチを採用。
- 元：9番「実測」
