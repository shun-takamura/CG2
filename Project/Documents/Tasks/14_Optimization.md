# 14. 最適化

> **目的: 最適化の余地を 1 か所に集める。** 各設計書で見つかった「重い所」と「軽くする候補」をここに書き、実施したら前後の実測を残す。
> 評価は動画＋ソース審査なので、**「自作プロファイラで測る → 原因を特定 → 直す → 測り直す」の記録そのものが語れる材料**になる。

最終更新: 2026-10-10

---

## 1. 書き方の決まり

- **1 件 = 1 節**。見出しは「対象（どの区間・どの場面）」。
- 必ず書く項目：

  | 項目 | 内容 |
  |---|---|
  | 状態 | 未着手 / 実施中 / 実施済み / 却下 |
  | 実測 | PEPPER の区間名と ms（ビルド構成・解像度・場面・日付）。未計測なら「未計測」と書く |
  | 原因 | 何が重いのか（推定なら推定と書く） |
  | 候補 | 軽くする案を、効果が大きく手間が小さい順に。見た目が変わるかも書く |
  | 元 | 見つけた設計書と節（例：9番 実測） |

- **実施したら**：前後の実測を同じ条件で取り、§5「実施済み」へ移す。却下した案も理由を残す（同じ案を二度検討しないため）。
- **計測は Development で取る。** Debug は D3D12 のデバッグ層が有効で、シェーダも最適化なし（`-Od`）の実行時コンパイルなので GPU 時間が過大に出る。
- 元の設計書には元の記述を残し、候補の追加・更新はここで行う。

## 2. 計測の道具

| 道具 | 使い方 | 出るもの |
|---|---|---|
| PEPPER（`PEPPER_SCOPE` / `PEPPER_GPU_SCOPE`） | 区間に 1 行入れる | `profile.log` に CPU / GPU の区間時間（1 秒ごと） |
| `PEPPER_GPU_STATS_SCOPE` | 半透明・塗りの重い区間に入れる（入れ子不可） | カウンタ「区間名.PSInv」＝描いた画素数×重なり。画面の画素数で割ると重なり枚数 |
| PEPPER の ImGui ウィンドウ（Debug） | 実行中に見る | 直近 1 秒の区間表とフレーム時間のグラフ |
| `/pepper` スキル | `profile.log` を渡す | 最遅区間 TopN と、該当コードを読んだ上での改善案 |
| 起動引数 | `--start-scene <名前>` / `--bench-hold <秒>`（その秒でレールを止める）/ `--scene-json <パス>` / `--no-raymarch-clouds` / `--no-clouds` / `--exit-after <秒>` | 同じ画面で条件を揃えて測る |
| `tools/Python/run_cloud_bench.py` | `--preset title / stage-planes / stage-raymarch`、`--mode "名前=引数"` で任意比較 | モードごとの区間の GPU 平均（中央値）の表 |
| `tools/Python/run_load_bench.py` | テクスチャロードの比較 | `Documents/load_bench_result.md` |
| `tools/Python/preview_cloud_raymarch.py` | 雲の式の CPU 版（見た目の確認用） | PNG。重さは測れない |

- 注意：GPU は負荷が軽いとクロックを下げるので、**軽い側の区間ほど遅めに出る**（9番 §4.2）。差を取る時は両方を同じ回数・交互に測る（`run_cloud_bench.py` はそうなっている）。

## 4. 候補（優先順）

### 4.1 雲のレイマーチ：降下中（入口〜出口の約 10 秒）

- **状態**：未着手
- **実測**：`CloudRaymarcher::March` 0 秒 0.31ms → 53 秒 **5.71ms**（フレーム 17.49ms で 60fps 割れ）／60 秒 5.21ms。`run_cloud_bench.py --preset stage-raymarch --seconds 20`、Development・RT 1/2 解像度、2026-10-10
- **原因**：
  - 穴のまわりの濃さ（`HoleOver`）：壁 2 面＋天井（その場所の上面の高さも引く）＋床で、ノイズの読み込みが通常の約 6 倍
  - B'（雲の中のもや）：1 歩ごとに濃さ 3 回（本体＋太陽側 2 タップ）× 3D 勾配ノイズ 2 オクターブ、48 歩
  - 縦穴のまわりの法線：濃さの中心差分で 6 回
- **候補**：
  1. `HoleOver` の天井・床を、その高さの近くにいる時だけ評価する（ほとんどの点は壁だけで済む）。見た目は不変
  2. B' の太陽側 2→1 タップ（B' 約 3 割減）。陰影が少し平らになる
  3. `volumeSteps` 48→32（B' 約 3 割減）。もやが少し粗くなる
  4. 3D ノイズを 1 オクターブ、または 3D テクスチャ（計算 → 読み込み 1 回）
  5. 降下中だけ RT を 1/2 → 3/8 解像度（全体が比例して減る）
  6. 縦穴のまわりの法線を中心差分（6 回）から前進差分（3 回＋手元の値の流用）に
- **目標**：60fps を保つには最低 1ms。①と②で届く見込み
- **元**：9番「実測」

### 4.2 地形の描画（ピクセルシェーダの塗り）

- **状態**：未着手（60fps は保てているので保留）
- **実測**：`Scene::DrawDynamicObjects`（地形込み）高高度 0.4〜0.7ms → 降下〜低空で地形が画面を埋めると **5〜8.7ms**。2026-10-08、Debug ログ（`Project/Logs/2026-10-08_223738` ほか）。影のパスは GPU 区間が無く未計測
- **原因**：頂点数は一定で、画面を埋めた時だけ増える → 地形 PS の塗りが主因とみる（推定）
- **候補**：
  1. 重みが 0 の層はテクスチャを引かない分岐（`Terrain.PS.hlsl:185-187`。岩の三平面 12 回・土 4 回を飛ばせる）。見た目は不変
  2. 岩の三平面投影で寄与の小さい面を飛ばす
  3. 異方性 16→8
  4. 影のパスに PEPPER の GPU 区間を足して頂点側も測る → 必要なら遠くの地形の LOD／チャンク分割＋視錐台カリング
  5. 三平面投影・2 スケールのサンプル数を減らす
  6. 影のカスケードの比率（`SetCascadeLambda`）の調整
- **元**：12番 §7・§8 後回し、11番 §3.4（L2→L8）

### 4.3 遠景の雲（Skybox の中の `CloudSky`）

- **状態**：未着手
- **実測**：`Skybox::Draw` 雲あり 1.84 / 雲なし 0.23ms（タイトル、2026-10-04）。ステージの高高度で 1.42ms（2026-10-10）、Debug ログでは 2.6〜2.9ms
- **原因**：空の全画面で 5 サンプル＋異方性 8（もこもこ有効時はさらに増える）
- **候補**：
  1. Skybox を不透明物・水面の**後**に描き、深度テストで隠れた画素を捨てる（画面の下半分は雲海や水面で隠れている）
  2. 異方性 8→4
  3. 下向き・フェード後の距離では早く抜ける（ミップ選択の微分に注意）
- **元**：9番 §4.2・「雲の最適化（条件付き）」

### 4.4 川の水面の反射に峡谷の地形が入る

- **状態**：未着手（未計測）
- **実測**：未計測。`CanyonTerrain`（約 70 万頂点）もタグ `Terrain` なので、川の反射のパスでも描かれる
- **候補**：
  1. PEPPER で `WaterReflection::Render` を測る
  2. 重ければ反射の対象から外す、または距離で絞る（13番 §4.3 の包む球の判定）
  3. 反射 RT の解像度を下げる
- **元**：11番 §3.4（L2→L3・L8）、13番 §4

### 4.5 スキニング・アニメーション（分身カウンター）

- **状態**：未着手（**機能のブロッカー**：分身のアニメ再生が性能理由で入れられていない）
- **実測**：スキン付き 4 体で fps が 40 台後半（計測済み、数値の記録は 8番）。PEPPER での区間計測は未実施
- **原因**（コード読解による推定。GPU のスキニングではなく CPU のアニメ適用）：
  - `ApplyAnimation` が毎フレーム・毎ジョイントで `std::map<std::string, NodeAnimation>` を文字列検索（`Skeleton.cpp:64`、ブレンド中は `:86`・`:95` で 2 回）
  - キーフレーム探索が毎回先頭からの線形走査（`Animation.cpp:79-86`）
- **候補**：
  1. ロード時にジョイント → チャンネルを事前解決して配列に持つ（毎フレームの文字列検索が消える）。効果大・手間小
  2. キーフレーム探索のカーソルキャッシュ（前回のインデックスから再開。逆再生・シークは 0 へ戻す）。効果大・手間小
  3. `DispatchSkinning` のバリア→Dispatch→バリアを全インスタンスでまとめる（`AnimatedObject3DInstance::DispatchSkinning`、`AnimatedObject3DInstance.cpp:201` 〜）。①②で足りなければ
- **進め方**：まず PEPPER で現状を測る（分身をスキン付きに戻した状態で）→ ① → 再計測 → ② → 再計測
- **元**：8番 §4

## 5. 実施済み

### 5.1 テクスチャロード：DirectStorage＋GDeflate＋pack 化

- **結果**（Development、全 .dds 94 枚・解凍後 108.8MB、各 5 回の中央値、ウォーム）：

  | 方式 | 実時間 | CPU サイクル |

  | Pack＋CPU 解凍 | 135.9ms | 274.9M |

- 詳細：`Documents/load_bench_result.md`

### 5.2 雲：板の雲とレイマーチの比較（判断の記録）

- 板の雲（smoke_00 の Plane）は**重なり画面 1 枚分 ≈ 0.04ms でほぼ線形**（100 枚 0.08ms → 800 枚 0.77ms）。高高度の雲海を埋めるなら 200〜400 枚で 0.2〜0.4ms、雲に近づくと 1〜2ms 以上に跳ねる見込み。
- レイマーチ（ゼノブレ式の面）は雲海の上で 0.31ms。**同じ桁で、近づいても量を増やしても一定**、雲を抜けられる → レイマーチを採用。
- 元：9番「実測」
